# MITTA — Decision Log

Engineering record of significant decisions. Each entry states the problem, the
options considered, what was chosen and why. Entries are append-only; if a
decision is reversed, a new entry supersedes it rather than editing history.

---

## DEC-001 — Desktop shell: Tauri v2

**Problem.** Need a cross-platform desktop shell for macOS and Windows.

**Options.** (a) Electron — mature, huge ecosystem, ~120 MB baseline, ships a
full Chromium. (b) Tauri v2 — Rust core, OS-native webview, ~10 MB baseline,
capability-based permission system. (c) Native per-OS (SwiftUI + WinUI) — best
integration, two full UI codebases.

**Decision.** Tauri v2.

**Why.** The product runs continuously in the background, so baseline RAM is a
recurring cost, not a one-off. Tauri's capability permission model also fits the
security requirements directly instead of being bolted on. Native was rejected
because maintaining two UIs contradicts the "majority of code shared" goal.

**Trade-off accepted.** Platform webview differences (WKWebView vs WebView2)
require real cross-browser testing. Smaller ecosystem than Electron.

## DEC-002 — Python backend as a PyInstaller sidecar

**Problem.** How does the Python backend get onto a user's machine and start?

**Options.** (a) PyInstaller binary bundled as a Tauri sidecar. (b) Bootstrap a
`uv` venv against system Python on first run. (c) Rust core with Python only for
AI.

**Decision.** (a) — compiled sidecar, spawned and supervised by Rust.

**Why.** Option (b) is better for development and worse for users: it fails on
machines with no Python, Microsoft Store Python, restricted PATH, or antivirus
that blocks writing executables into AppData — and it fails at first launch, the
worst possible moment. PyInstaller shifts that cost into our build pipeline
where it is repeatable. Option (c) is the better long-term answer for hot paths
and is partially adopted in DEC-003 rather than wholesale.

**Trade-off accepted.** 150–300 MB bundle; slower release builds; PyInstaller
hidden-import issues must be managed in CI.

## DEC-003 — OS responsibility split between Rust and Python

**Problem.** Both Rust and Python can perform OS operations. Which owns what?

**Decision.** Rust owns shell-level OS concerns (tray, global hotkey, window
management, system metrics, screenshots, secret storage, confirmation dialogs).
Python owns application automation (AppleScript/PowerShell, file operations,
git, docker, browser control) and all reasoning.

**Why.** Rust already holds the event loop, window handles and OS permissions.
System metrics are sampled continuously, where `sysinfo` in Rust costs a
fraction of a `psutil` poll loop over a multi-hour session. Everything iterated
on frequently stays in Python, where the AI ecosystem lives.

**Alternative considered.** All OS access in Python via `psutil`/`pyobjc` —
simpler, one language, but measurably worse idle cost and no clean way to make
confirmation dialogs untamperable.

## DEC-004 — Transport: authenticated loopback WebSocket + HTTP

**Problem.** How do the UI and sidecar communicate?

**Decision.** FastAPI on `127.0.0.1` with an **ephemeral** port. WebSocket for
streaming (tokens, voice, task progress, metrics), HTTP for CRUD. Every request
carries a 256-bit session token generated by Rust at spawn.

**Why.** A fixed port can be squatted by another local process or collide with a
second instance. The token prevents any other local process from driving the
agent. Streaming is a first-class requirement, so WebSocket is the primary
channel rather than an add-on.

## DEC-005 — SQLite as system of record, FAISS as derived cache

**Problem.** Memory needs both structured queries and semantic search.

**Options.** (a) FAISS authoritative for vectors, SQLite for metadata.
(b) SQLite authoritative, FAISS a rebuildable derived index. (c) A single
embedded vector DB (LanceDB/Chroma).

**Decision.** (b).

**Why.** FAISS index files are not crash-safe and have no transactional story.
Making them authoritative means a corrupted file is permanent data loss. Making
them derived turns the same event into a 30-second re-index. Every vector row
carries its source SQLite id and the embedding model id, so migrations are
detectable. SQLite runs in WAL mode so background consolidation doesn't block
reads.

**Alternative considered.** (c) is a smaller moving-parts count but less mature
and less inspectable than SQLite, which the user can open with any tool.

## DEC-006 — Embeddings run locally, always

**Problem.** Semantic memory needs an embedding model.

**Decision.** `bge-small-en-v1.5` via ONNX Runtime — 384-dim, ~130 MB, CPU-fast,
no key, no network.

**Why.** Cloud embeddings would make every memory write a billable network
round-trip and would stop memory working offline, contradicting the product's
first principle. Embedding quality at this tier is more than adequate for
personal-scale retrieval.

**Trade-off accepted.** Model is pinned; changing it forces a full re-index.

## DEC-007 — Free-first, task-aware model routing

**Problem.** Requirement is "free and best", which are in tension.

**Decision.** Resolve per task class rather than globally. Tier 0 local
(Ollama/LM Studio, auto-detected) → Tier 1 free cloud tiers (Groq, Gemini) →
Tier 2 BYOK paid (Anthropic, OpenAI, DeepSeek, OpenRouter). Planning routes to
best-available; personality rewrite routes to cheapest-fastest; background
summarisation prefers local; embeddings are always local.

**Why.** A single global model choice forces either paying for trivial calls or
accepting weak planning. Task-aware routing gets quality where it is felt and
costs nothing where it isn't.

**Trade-off accepted.** Fully offline, multi-step planning degrades noticeably.
The design makes this graceful, not invisible.

## DEC-008 — Personality as a terminal, constrained rewrite stage

**Problem.** Style must not compromise reasoning.

**Decision.** Personality is the final pipeline stage, taking text in and text
out, with hard pass-through rules for code, paths, commands, URLs, numbers,
refusals and confirmation prompts. Toggleable, with intensity; a no-op at zero.

**Why.** Structural isolation is stronger than instructional isolation. Because
the layer never sees tools or memory and runs after all decisions are made, it
is incapable of changing one. Injecting style into the system prompt instead
was rejected precisely because it *would* influence reasoning.

**Alternative considered.** Fine-tuning a model on the style — better fidelity,
but locks the product to one provider and violates the abstraction requirement.

---

## DEC-009 — Plugins out-of-process, MCP-compatible

**Problem.** Third-party extensibility without compromising stability or safety.

**Decision.** Plugins are separate subprocesses speaking JSON-RPC over stdio,
using an MCP-compatible protocol, with declared permissions enforced by the
policy engine.

**Why.** In-process plugins can crash the assistant and can reach around the
policy engine by sharing the interpreter. Isolation solves both. Choosing
MCP compatibility rather than a bespoke protocol means the existing MCP server
ecosystem becomes installable MITTA plugins at zero additional cost — the
highest-leverage decision in the plugin design.

**Trade-off accepted.** Per-plugin process overhead and serialisation cost.

---

## DEC-010 — Confirmation prompts rendered by Rust, approval tokens signed

**Problem.** Destructive actions need approval that the requester cannot forge.

**Decision.** The Rust shell renders confirmation UI. Approval returns a signed,
single-use, expiring token bound to that exact tool call and parameters. Python
verifies the token before execution.

**Why.** If the Python process both requests and confirms, a prompt-injected
agent can approve its own destructive action — the guard becomes decorative.
Moving the trust boundary to the process that isn't running model output is the
entire value of the control.

## DEC-012 — Personality vocabulary: one dataset token excluded

**Problem.** The source style dataset's frequency list includes a racial slur as
a high-frequency token (14 occurrences), and the user confirmed it as a
characteristic verbal pattern.

**Decision.** Reproduce the *structure* of the pattern — emphatic all-caps
vocative triads, doubled affirmation, blunt one-word verdicts — using the
speaker's other attested vocatives (`vro`, `ra`, `re`, `nga`). The slur itself
is excluded from the generation vocabulary.

**Why.** Claude will not build a generator that emits racial slurs. The stylistic
signal that makes the voice recognisable is carried by the *form* — caps,
repetition, vocative-plus-verdict rhythm — not by that specific token, so
fidelity loss is minimal.

**Alternative considered.** A user-configurable vocabulary allowing it. Rejected
for the same reason.

## DEC-013 — macOS-first; Windows abstraction without implementation

**Supersedes the platform scope in DEC-001 and DEC-003.**

**Problem.** Cross-platform from day one doubles the surface area of every OS
touchpoint before a single user has validated the product.

**Options.** (a) Build both now. (b) macOS only, no abstraction — add Windows
later via refactor. (c) macOS implementation behind a full OS abstraction, with
a `WindowsAdapter` stub.

**Decision.** (c). *(Product owner decision.)*

**Why.** (b) is the trap: platform assumptions leak everywhere — path
separators, `osascript` calls, Keychain access, bundle layout — and become a
month of archaeology later. Keeping the boundary while writing one
implementation costs a little now and preserves the option cheaply.

**Enforcement.** No `osascript`, no `~/Library` path and no AppleScript string
may appear above the OS Adapter boundary. The `WindowsAdapter` stub raises
`NotImplementedError` to document the contract.

**Trade-off accepted.** A single-implementation abstraction is genuinely harder
to get right than one written against two — the boundary will be wrong in places
and only Windows work will reveal where.

## DEC-014 — Provider set: Groq primary, OpenRouter secondary, with failover

**Amends DEC-007.** The free-tier routing ladder is replaced by a confirmed
two-provider set.

**Decision.** Groq as primary, OpenRouter as secondary, health-based automatic
failover. Ollama, Anthropic, OpenAI, Gemini and DeepSeek adapters are deferred
but the interface accommodates them unchanged.

**Why.** OpenRouter is a strong second leg precisely because it is not a single
vendor — it is itself a multi-provider gateway, so a Groq outage or rate-limit
can be served by a comparable model without code changes. Groq leads because its
latency is the best available on a free tier, which matters for a voice-driven
assistant where round-trip time is felt directly.

**Trade-off accepted.** Both legs are cloud. With Ollama deferred, v1 has **no
offline inference** — memory and retrieval still work offline, but reasoning
does not. This narrows the original "work offline with local models" goal and is
flagged as an open question rather than settled.

## DEC-015 — Local-only storage, ratified

**Confirms DEC-005 and DEC-006 as hard requirements rather than defaults.**

**Decision.** SQLite + FAISS + local filesystem. Firebase, Supabase, MongoDB
Atlas and every hosted database, vector service or sync service are prohibited
without exception. *(Product owner decision.)*

**Why.** This retroactively validates DEC-006 (local embeddings). Had embeddings
been routed to a cloud API, every memory write would have shipped user content
off-machine, and R5 would have been unenforceable no matter what the database
was. The storage decision and the embedding decision are the same decision.

## DEC-016 — Privacy enforced at a chokepoint, not by convention

**Problem.** "Only send what's needed" is a property that decays silently — any
future component can quietly widen the payload and nothing fails.

**Decision.** Context assembly is the **only** component permitted to construct
an outbound payload. It applies a hard budget and records every payload locally
for inspection in the UI.

**Why.** A rule enforced in one place can be tested; a rule enforced by
discipline across twenty call sites cannot. Making payloads user-inspectable
turns the guarantee into something verifiable rather than something claimed.

---

## DEC-017 — Secrets in Keychain only, entered via UI

**Problem.** API keys leak through config files, `.env`, shell history, logs and
crash dumps.

**Decision.** Keys live only in the macOS Keychain, written by the Rust layer.
Entry is through the settings UI — never a file, never a CLI argument (which
would expose them in the process list), never an environment variable in a
committed file. Log formatters carry a redaction filter for key-shaped strings.

**Why.** Every convenience path for key entry is also a leak path. Closing all
of them costs one settings screen.

## DEC-018 — Three surfaces over one state layer

**Problem.** The reference set spans two incompatible shapes: Raycast is a
transient overlay, Cursor and Linear are persistent windows.

**Decision.** Build all three — menu bar item, global-hotkey command palette,
and a persistent main window — as front-ends over **one** state layer.
*(Product owner decision.)*

**Why.** The required surfaces (project explorer, memory explorer, system
monitor, history) need a persistent window, while the "always one keystroke
away" quality that makes Raycast and Warp worth imitating needs an overlay.
Both are real requirements.

The load-bearing constraint is *one state layer*. Two surfaces over two state
models is how this design fails: they drift, the same action behaves differently
in each, and a command started in the palette can't be continued in the window.
Sharing state makes the palette a *view*, not a second app.

**Trade-off accepted.** The most UI work of the available options, and the
palette's sub-100 ms open budget constrains what may block first paint.

## DEC-019 — Speech runs native-side, not in Python

**Amends the DEC-003 responsibility split.**

**Problem.** Apple's `Speech` and `AVFoundation` frameworks are Swift/ObjC-only.
Python has no first-class access.

**Decision.** STT and TTS move to the Rust/Swift layer. Python consumes
transcripts and emits synthesis requests over the existing local RPC.

**Why.** This is a *consequence* of choosing the native stack, not an
independent choice — worth recording because it moves a whole architectural
layer across the process boundary. Bridging Apple frameworks into Python via
`pyobjc` was rejected: it would put a fragile bridge on the latency-critical
audio path, and PyInstaller bundling of `pyobjc` is a known source of packaging
failures.

**Why the native stack at all.** Zero model downloads against 1–2 GB for
Whisper + Piper, meaningfully lower idle RAM, faster cold start, and Apple
handles microphone permissions and audio-session management natively.

**Trade-off accepted.** Ties the speech layer to macOS. A Windows port needs a
fresh implementation rather than a recompile — acceptable under DEC-013, and the
adapter boundary is what keeps it contained.

## DEC-020 — Ollama deferred entirely

**Problem.** Both confirmed providers are cloud. Does v1 ship offline reasoning?

**Options.** (a) Full Ollama support. (b) Write the adapter, ship it disabled.
(c) Defer entirely.

**Decision.** (c). *(Product owner decision — my recommendation was (b).)*

**Why (owner's rationale).** Ollama is not installed, both providers are
adequate, and it removes a multi-GB dependency from v1.

**Risk I flagged.** An interface with one kind of implementation tends to encode
that kind's assumptions. A cloud-only gateway can silently bake in API keys as
mandatory, per-token cost as always-present, uniform tool-calling support, and
network errors as the only failure mode — none of which hold for a local server.

**Mitigation, since the decision stands.** The gateway interface will be
*designed* against local-provider requirements even though no local adapter is
written: authentication optional rather than required, cost model nullable,
tool-calling support declared as a capability rather than assumed, and
"unavailable" distinguished from "errored". This costs nothing now and keeps the
retrofit cheap.

**Trade-off accepted.** No reasoning without a network in v1. Memory, retrieval,
semantic search and the UI all still work offline.
